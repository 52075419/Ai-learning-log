## 一、需求拆解——把“想法”变成“步骤”

### 1.1 为什么需要拆解

“做一个代码解释器”这句话没法直接变成代码——输入是什么？输出是什么？出错怎么办？一次处理多少？全都没说。

需求拆解，就是把模糊的“想法”拆成清晰、可执行、可验证的“小任务”。

### 1.2 拆解的三步法

**第一步：写清楚“输入 → 处理 → 输出”**

| 要素 | 问自己 | 例子（代码解释器） |
|------|--------|-------------------|
| 输入 | 用户给什么？什么格式？ | 一段 Python 代码，纯文本 |
| 处理 | 中间做什么？ | 调用 DeepSeek API，让它解释代码 |
| 输出 | 用户看到什么？什么格式？ | 一段中文解释，打印在屏幕上 |

**第二步：拆成“可独立完成的小任务”**

1. 能读取用户输入的代码
2. 能组装 Prompt（含角色、任务、约束）
3. 能调用 API 并拿到响应
4. 能解析响应、取出解释文本
5. 能处理出错情况
6. 能把结果打印出来

每个小任务，都应该是“能单独写、能单独测”的。

**第三步：给每个任务定“完成标准”**

| 任务 | 完成标准 |
|------|---------|
| 读取输入 | 能从命令行读到一段代码，打印确认 |
| 组装 Prompt | Prompt 里包含角色、任务、约束、格式四要素 |
| 调用 API | 能拿到 200 响应，打印原始 JSON |
| 解析响应 | 能从 JSON 里取出 content 字段 |
| 处理错误 | Key 错误时打印“认证失败”，而不是崩溃 |
| 打印结果 | 解释文本能完整显示 |

完成标准要具体到“能看到什么”，而不是“做好了”。

### 1.3 不拆解会怎样

直接写 200 行脚本，一跑报错，不知道错在哪一步——读文件错了？Prompt 拼错了？API 返回格式变了？还是解析写错了？

拆解之后，每一步都能单独验证，出错时能快速定位。

### 1.4 实用原则：先跑通“最小闭环”

先做一个能跑通的最小版本：读一段写死的代码 → 调 API → 打印解释。跑通了，再逐步加：读文件、处理错误、支持多段代码。

先能跑，再做好。

## 二、代码组织——代码放哪、怎么分、怎么起名

### 2.1 为什么需要组织

写 10 行放一个文件没问题；写 200 行、500 行全塞一个文件，就会：找个函数翻半天、改一处不知影响哪、报错不知错在哪个逻辑块。

代码组织，就是让代码“好找、好改、好读”。

### 2.2 文件怎么分

原则：按“职责”分文件，一个文件干一类事。

以代码解释器为例：

| 文件 | 职责 |
|------|------|
| main.py | 程序入口：读输入、调流程、打印结果 |
| api_client.py | 只负责和 DeepSeek API 打交道 |
| prompt.py | 只负责拼 Prompt |
| config.py | 存配置（API Key、模型名、temperature） |

不是文件越多越好，小项目 2～4 个文件足够。

### 2.3 函数怎么组织

一个函数只做一件事。判断标准：能用一句话说清它在干嘛，且这句话里没有“然后”。

- ❌ 差：`process()` —— 读代码，然后调 API，然后解析，然后打印
- ✅ 好：`read_input()`、`build_prompt()`、`call_api()`、`parse_response()`、`print_result()`

函数名用动词开头，一眼看出在干嘛。

### 2.4 命名规则

| 类型 | 规则 | 例子 |
|------|------|------|
| 变量/函数 | 小写 + 下划线 | user_input、call_api |
| 常量 | 全大写 + 下划线 | API_URL、MAX_TOKENS |
| 类 | 大驼峰 | ApiClient |

不要用 a、b、data1、temp 这种看不出含义的名字（循环变量 i 除外）。

### 2.5 一个简单的目录结构

```
code-explainer/
├── main.py
├── api_client.py
├── prompt.py
├── config.py
└── requirements.txt
```

requirements.txt 里写依赖的库，一条 `python -m pip install -r requirements.txt` 就能装好。

### 2.6 常见误区

过早追求“完美架构”。小项目先按职责分几个文件、函数写清楚就够了，等项目大了再重构。

## 三、调试——程序报错了，怎么定位、怎么修

### 3.1 调试是什么

调试 = 找到“程序为什么没按预期运行”的原因，并修好它。调试能力，就是“快速定位问题”的能力。

### 3.2 第一步：读懂报错信息

Python 报错信息从下往上看：

- 最后一行：错误类型和原因
- 往上：调用链（哪个文件、哪一行、调了什么）

先看最后一行知道“什么错”，再看往上知道“在哪错”。

### 3.3 第二步：用 print 缩小范围

在关键位置打印中间结果：

```python
print("1. 读到输入：", user_input[:50])
print("2. 拼好 Prompt：", prompt[:100])
print("3. API 返回状态码：", response.status_code)
print("4. 返回内容：", response.text[:200])
```

看打印到第几步停了/不对了，问题就在那附近。这是最朴素、最有效的调试方法。

### 3.4 常见错误类型及原因

| 错误 | 常见原因 | 怎么查 |
|------|---------|--------|
| SyntaxError | 少括号、少冒号、缩进错 | 看报错行号，检查符号 |
| NameError | 变量名拼错、没定义 | 检查变量名是否一致 |
| TypeError | 类型不匹配 | 打印变量类型 type(x) |
| KeyError | 字典键不存在 | 打印字典内容，看有哪些键 |
| IndexError | 列表越界 | 打印列表长度 len(lst) |
| AttributeError | 对象没有这个属性/方法 | 检查拼写、检查对象类型 |
| 网络错误 | 超时、连不上、401/429 | 打印 status_code 和 response.text |

### 3.5 第四步：假设 → 验证 → 修正

1. 假设：“我猜是 API Key 没传对”
2. 验证：打印 headers，看 Authorization 对不对
3. 修正：改对后重跑，看是否解决

一次只改一个地方，改多了不知道是哪个起的作用。

### 3.6 调试的三个好习惯

1. 先复现：能稳定复现的错误，才好修
2. 从简：把复杂输入换成最简单的，看还报不报错
3. 别猜太久：猜了两次不对，就加 print 或查文档

### 3.7 一个反例

报错 KeyError: 'choices'，不看报错，直接改 Prompt、改 temperature、改模型名——改了半小时，问题其实是“Key 错了，API 返回错误信息，根本没有 choices 字段”。

先读报错，再动手。

## 四、测试——怎么判断程序“真的对了”

### 4.1 测试是什么

测试 = 用已知答案的输入，验证程序输出是否符合预期。

调试是“出错后修”，测试是“主动找错”。不测试，你只是“觉得它对了”，不是“知道它对了”。

### 4.2 最简单的测试：手动验证

准备“输入 + 预期输出”，跑一遍，对比。关键是：先写预期，再看实际，不要“看它输出啥然后觉得差不多就行”。

### 4.3 测试的三种层次

| 层次 | 测什么 | 例子 |
|------|--------|------|
| 单元测试 | 单个函数对不对 | build_prompt() 返回的字符串里有没有“角色” |
| 集成测试 | 几个模块串起来对不对 | 读输入 → 调 API → 解析，整条链路通不通 |
| 端到端测试 | 从用户输入到最终输出整体对不对 | 贴一段代码，最终打印的解释是否合理 |

小项目至少做“手动端到端测试”：准备 3～5 个典型输入，手动跑，看输出。

### 4.4 测试用例怎么选

不要只测正常情况，要覆盖：

| 类型 | 例子 |
|------|------|
| 正常输入 | 一段普通 Python 代码 |
| 边界输入 | 空字符串、超长代码、只有一行 |
| 异常输入 | 不是代码的文本、含特殊字符 |
| 错误场景 | API Key 错误、网络断开 |

异常输入和错误场景最容易被忽略，也最容易出问题。

### 4.5 对 AI 应用的特殊测试

AI 应用输出不固定，测试要调整：

- 不追求逐字一致，追求关键点是否覆盖
- 多跑几次，看输出是否稳定
- 人工判断：准备“预期要点清单”，逐条核对

例：测代码解释器，预期要点清单——① 说明整体功能 ② 提到关键函数/语句 ③ 没编造代码里不存在的内容。

### 4.6 测试记录

```
测试日期：2026-11-10
输入：print("hello")
预期：解释中提到“输出 hello”
实际：解释为“打印字符串 hello 到屏幕”
结论：✅ 通过

输入：（空字符串）
预期：提示“请输入代码”
实际：程序崩溃，报错 IndexError
结论：❌ 不通过，需修复
```

记录的价值：改代码后能快速回归测试，确认没改坏。

## 五、版本与迭代——改坏了怎么回退、怎么小步快跑

### 5.1 为什么需要版本管理

开发中一定会遇到：改完发现“还不如不改”、加功能加崩了、想试新写法又怕改坏好的。

版本管理就是给代码“存档”和“读档”的能力。

### 5.2 Git 的最小用法

| 操作 | 命令 | 什么时候做 |
|------|------|-----------|
| 初始化 | git init | 项目开始时一次 |
| 查看状态 | git status | 随时，看哪些文件改了 |
| 添加 | git add . | 准备提交前 |
| 提交 | git commit -m "说明" | 完成一个小功能/修复后 |
| 查看历史 | git log --oneline | 想回看/找回时 |

核心习惯：每完成一个“小任务”，就 commit 一次。不要攒一天再提交。

### 5.3 commit 信息怎么写

一句话说清“这次改了什么”：

- ❌ update、fix bug、修改
- ✅ 添加读取命令行输入的功能
- ✅ 修复 API Key 错误时崩溃的问题

信息写清楚，回看历史时才知道每次改了什么。

### 5.4 小步快跑：迭代的节奏

不要“憋一个大功能，写三天再跑”。正确节奏：

```
写一小步 → 跑一下 → 对了 → commit → 写下一小步
```

每一步都保持“能跑”的状态。任何一步出问题，都能快速定位，也能随时回退到上一个“能跑”的版本。

### 5.5 改坏了怎么回退

| 情况 | 做法 |
|------|------|
| 刚改的还没 commit，想撤销 | git checkout -- 文件名 |
| 已 commit 但想回到上一个版本 | git log 找到版本号，git reset --hard 版本号（慎用） |
| 想看某次改了什么 | git show 版本号 或 git diff |

现阶段记住：“每小步 commit”就是最好的保险。

### 5.6 提交前自检

commit 前问自己三句：

1. 这个改动能跑吗？（至少跑一次）
2. 这个改动只做了一件事吗？
3. commit 信息说清了吗？

### 5.7 版本管理与“用 AI 写代码”的关系

AI 帮你改代码时，先 commit 当前能跑的版本，再让 AI 改。改完跑一遍，不对就回退。有 Git 兜底，你才敢让 AI 大胆改。
